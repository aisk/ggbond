# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

GGBond is an object-oriented Python wrapper over GGML (Georgi Gerganov's Machine Learning library). The OO layer (`ggbond.ggml`) is implemented in **pure Python on top of [`ggml-python`](https://github.com/abetlen/ggml-python)** (a ctypes binding to GGML) — there is no C/C++ source, no compiled extension, and no GGML submodule in this repo. The actual GGML shared library ships inside the `ggml-python` dependency.

- **Language**: Pure Python 3.10+
- **Build backend**: `hatchling` (pure-Python wheel, no compilation step)
- **Dependencies**: `ggml-python>=0.0.45` (provides the `ggml` ctypes module and `ggml.utils`) and `numpy` (the data-transfer API is numpy-based).

All library code lives under **`ggbond/ggml/`**. Every checked-in example uses the current API: `simple.py`, `gpt2.py`, `magika.py`, and `nam.py`. The model-backed examples require external model files.

```bash
.venv/bin/python examples/simple.py            # or: uv run examples/simple.py

# Regenerate the type stub of the generated ops after touching an op table
.venv/bin/python scripts/gen_stubs.py
```

The standard-library `unittest` suite lives under `tests/`. `examples/simple.py` is the numerical smoke test.

### Backend availability
Backend factories live in `ggbond/ggml/backend.py`; the GPT-2 and NAM examples provide their own `_init_backend` CLI dispatch. Whether `cuda`/`metal`/`hip` actually work depends on **how the installed `ggml-python` package was built** (this repo does not build GGML). `cpu` is always available. Unavailable optional backends raise `GGMLError`.

## Architecture

Everything live lives under **`ggbond/ggml/`** — a thin OO wrapper whose classes map to GGML concepts and whose methods map ~1:1 to `ggml_*` / `gguf_*` C functions. Computation is **explicit and two-phase; nothing is lazy**.

| Module | Class | Wraps / Notes |
|--------|-------|---------------|
| `errors.py` | — | Defines `GGMLError`, `check_status`, `status_name`, `nonnull`. Each module imports the bindings directly as `import ggml as _ggml` (and `from ggml import utils as _utils` in `types.py`) — Python 3 absolute imports resolve `ggml` to the site-packages package, never the `ggbond.ggml` subpackage; the `_ggml` alias keeps the external package visually distinct. |
| `handle.py` | `Handle` | Base class of every wrapper that owns a native pointer (`Context`, `Backend`, `Buffer`, `GAllocr`, `Scheduler`, `GGUF`). Subclasses set `_ptr` and implement `_free(ptr)`; the base supplies `ptr` (raises `GGMLError` once closed), `closed`, idempotent `close()`, `with` support and `__del__`. |
| `log.py` | `LogLevel` | `log_set(callback)` wraps `ggml_log_set`: `callback(level, text)`, and `None` restores ggml's stderr default. |
| `ops.py`, `ops.pyi` | `TensorOps`, `ContextOps` | Empty holder classes the generated op methods are installed on; `Tensor` and `Context` inherit from them. They exist so `ops.pyi` (generated by `scripts/gen_stubs.py`, never edited by hand) can describe the `exec`-generated methods to type checkers and IDEs. `ggbond/py.typed` marks the package as typed. |
| `types.py` | `DType` | Reuses `ggml.utils.GGML_TYPE` directly (values never drift). Aliases `F32`, `F16`, `I32`, … and `dtype_from_numpy` / `dtype_to_numpy`. |
| `context.py` | `Context` | `ggml_context`. Constructor takes `mem_size` (bytes, positional) + `no_alloc=True` / `mem_buffer`. Size it for tensor metadata + graphs (and tensor data when `no_alloc=False`); `examples/simple.py` uses `1 << 20`. `Context.for_tensors(n, graph_size=…)` does that arithmetic for `no_alloc` metadata contexts. Factories: `new_tensor_1d/2d/3d/4d(dtype, *ne, name=…)`, the variadic `new_tensor(dtype, *ne, name=…)`, `arange(start, stop, step)`, `new_graph()`. `reset()` (`ggml_reset`) empties the arena for reuse and retires every tensor and graph created so far. `from_ptr()` wraps an externally created context (e.g. the one `gguf_init_from_file` fills in). **Every ggml op is a method here with C's argument order**: `ctx.mul_mat(a, b)` is `ggml_mul_mat(ctx, a, b)`, and the result lands in `ctx` whichever contexts the operands live in. That is how a graph reads model weights or a KV cache held in another context. A context records the other contexts its ops read from (`_deps`) and keeps them alive. |
| `tensor.py` | `Tensor` | A `(Context, ggml_tensor_p)` pair, where the context is the one owning the tensor's metadata. Op methods are sugar for the context form: `a.add(b)` is `a.ctx.add(a, b)`. **All** ops are table-generated from `_UNARY_OPS` / `_BINARY_OPS` / `_PARAM_OPS` onto both `Tensor` and `Context` (see "Adding / changing ops"), plus an `<op>_inplace` variant wherever the bindings have `ggml_<op>_inplace`; the tables cover elementwise math, reductions, normalization, attention (`rope`, `rope_ext`, `soft_max_ext`, `flash_attn_ext`, `diag_mask_inf`), shape (`reshape_*`, `cont_*`, `view_1d`…`view_4d`, `permute`, `concat`, `pad`, `repeat*`), the `set*` graph ops, and convolution/pooling. `ne`/`nb` are the four dims/strides ggml stores; `shape` is numpy order. Also exposes `flags`, `src`, `view_src`, the `is_*` predicates and `set_input/output/param/loss`. Two wrappers of one `ggml_tensor` are equal and hash alike. **This is where numpy lives**: `write(x)` uploads any array-like (incl. plain Python lists — runs `np.ascontiguousarray` and checks the shape), `write_raw(data, offset)` uploads any bytes-like buffer verbatim without copying it, `read(out)` downloads into a **pre-allocated numpy array**, `to_numpy()` allocates that array for you, and `copy_to(dst)` is `ggml_backend_tensor_copy`. They are not called `set`/`get` because `ggml_set` is a graph op. `+`/`-`/`*`/`/`/unary `-` map to the element-wise ops, scalar `*`/`/` map to `scale` and scalar `+`/`-` to `scale_bias`, `t.T` is `transpose`, and `np.asarray(t)` downloads via `to_numpy`. Each operator is exactly one ggml op, so `2.0 / t` and `**` are unsupported. There is deliberately **no** `@` for `mul_mat`. The transfers wrap ggml's sync `ggml_backend_tensor_set/get`, which are keyed on the tensor's own buffer and take **no backend handle** — hence they live on `Tensor`, not `Backend`. The tensor must already be allocated. |
| `graph.py` | `Graph` | `ggml_cgraph`. Holds a strong ref to its backing `Context`; no independent `close()` (freed with the context). `build_forward_expand()`, `build_backward_expand()` / `get_grad()` / `reset()` for `grads=True` graphs, `clear()`, `compute_with_ctx()` (CPU-only convenience for `no_alloc=False`), `nodes()` / `leafs()` / `get_tensor()` via struct fields, and `print()` / `dump_dot(path)` for debugging. Tensors returned from a graph are bound to the context that really owns them (`Context._adopt` finds the arena containing the pointer). |
| `gallocr.py` | `GAllocr`, `GraphAllocator` | `ggml_gallocr`. `from_backend(be)`, `reserve()`, `alloc_graph()`. `GraphAllocator` is the base it shares with `Scheduler`: an allocator holds one graph at a time, and the base remembers the tensors it allocated for that graph (by address, grouped by owning context) and unallocates them before a different graph is allocated and when the allocator's buffers are regrown or freed (see Lifecycle rules). Subclasses call `_allocating(graph)` before and `_allocated(graph)` after every ggml call that allocates a graph, and `_reserved()` after a reserve. |
| `backend.py` | `Backend` | CPU/CUDA/Metal/HIP handle. Use `Backend.cpu_init()` / `cuda_init()` / `metal_init()` / `hip_init()`, or the device registry: `Backend.load_all()` then `Backend.init_best()` / `init_by_type(DeviceType.…)` / `init_by_name("CUDA0")`. The constructor itself adopts a raw backend pointer. `buffer_type`, `device`, `name`, `is_cpu` are properties; `supports_op(t)` / `offload_op(t)` query op support. `close()` first closes every still-open `Buffer`, `GAllocr` and `Scheduler` built on the backend (tracked weakly). Tensor data transfer is **not** here (it lives on `Tensor`, see above). |
| `device.py` | `Device` | `ggml_backend_dev_t` from the backend registry. `Backend.load_all()` then `Device.all()` / `Device.by_name()` / `Device.by_type()`; each device reports `name`, `description`, `type`, `buffer_type`, `memory()` (free, total), and `init_backend()` opens a `Backend` on it. Devices are owned by the registry, so `Device` has no `close()`. |
| `buffer.py` | `Buffer`, `BufferType` | `ggml_backend_buffer_t` and `ggml_backend_buffer_type_t`. `Backend.alloc_ctx_tensors()` returns a `Buffer` (`size`, `name`, `is_host`, `buffer_type`, `clear()`). As in ggml the buffer is its own resource and `close()` frees it; the context it was allocated for keeps it alive, so the return value can be ignored. `Backend.buffer_type` returns a `BufferType`, which `GAllocr` and `Scheduler` also accept as a raw pointer. |
| `scheduler.py` | `Scheduler` | `ggml_backend_sched`. Splits a graph across one or more backends and computes it — the multi-backend analog of `GAllocr` + `Backend.compute`. `Scheduler(gpu, cpu, …)` takes its backends as positional arguments in priority order. Holds strong refs to its `Backend`s so they outlive it; `close()` frees only the `ggml_backend_sched` (the backends are owned by their own wrappers). `n_splits` / `n_copies` are properties; `buffer_size(backend)` is the compute buffer held for one backend. The last backend must be a CPU backend (`ValueError` otherwise). The scheduler holds **one allocated graph at a time**: `alloc_graph` (or a `compute` that allocates for you) makes a graph current and `reset()` releases it, so every evaluation is `reset()` → build → `alloc_graph()` → upload → `compute()`. The wrapper tracks the current graph (`_current`) and raises `GGMLError` for a second `alloc_graph`, for computing a graph other than the current one (ggml would silently compute the old one, or crash if its context was reset), and for a graph with more nodes + leafs than `graph_size` allows. |
| `gguf.py` | `GGUF` | `gguf_context` (parsed GGUF header/metadata). `from_file(path)` parses via `gguf_init_from_file` and, by default, also wraps the metadata `ggml_context` it fills as `.context`. **Ownership is split**: `GGUF.close()` frees only the `gguf_context`; `.context` is an independently owned `Context` you must close yourself (and that must outlive any graph referencing its tensors). `GGUF` does *not* read tensor data — `data_offset` / `get_tensor_offset` / `get_tensor_name` give the caller what they need to seek into the file and upload weights. Typed `get_val_*` / `set_val_*` accessors are generated from `_KV_TYPES`; `value(key)`, `gguf[key]`, `key in gguf`, `get()`, `keys()` and `items()` dispatch on the stored type for you. Writing is supported too: `init_empty()`, the setters, `set_arr_data` / `set_arr_str`, `add_tensor`, `set_tensor_data` / `set_tensor_type`, `write_to_file`. |

Every ggml enum is an `IntEnum` whose values come straight from the bindings: `DType`, `Op` (what `Tensor.op` returns; generated from `GGML_OP_*`), `PoolOp`, `RopeType`, `SortOrder`, `ScaleMode`, `TensorFlag` (an `IntFlag`), `DeviceType`, `GGUFType` and `LogLevel`. Only the common dtypes have module-level aliases (`F32`, `I32`, …); everything else is spelled through its enum (`PoolOp.MAX`, `DeviceType.CPU`). Every parameter typed as one of these still accepts a plain int.

Naming rule: methods keep the ggml function name minus its prefix (`Backend.cpu_init`, `Graph.build_forward_expand`). A getter that takes no argument and reads a fixed attribute of the object is a property (`Tensor.ne`, `Backend.buffer_type`, `Scheduler.n_splits`); getters with arguments or that sample changing state stay methods (`GGUF.get_key(i)`, `Device.memory()`).

`ggbond/__init__.py` exports only `__version__`. Import all wrapper classes and constants explicitly from `ggbond.ggml`.

### Canonical computation flow

GGML is two-phase. The pattern (see `examples/simple.py` and the `ggbond/ggml/__init__.py` docstring):

```python
import numpy as np
from ggbond.ggml import Backend, Context, GAllocr, F32

a = np.random.rand(4, 3).astype(np.float32)
b = np.random.rand(2, 3).astype(np.float32)

with Backend.cpu_init() as be, \
        Context(mem_size=1 << 20, no_alloc=True) as ctx:
    be.set_n_threads(4)
    ta = ctx.new_tensor_2d(F32, *reversed(a.shape), name="a").set_input()
    tb = ctx.new_tensor_2d(F32, *reversed(b.shape), name="b").set_input()
    tc = ta.mul_mat(tb).set_output()                            # ctx.mul_mat(ta, tb): b @ a.T

    be.alloc_ctx_tensors(ctx)                                  # allocate backend memory for ctx tensors
    ta.write(a)                                                # upload via the tensor (lists also accepted)
    tb.write(b)

    graph = ctx.new_graph().build_forward_expand(tc)
    with GAllocr.from_backend(be) as alloc:
        alloc.alloc_graph(graph)                               # allocate working memory
        be.compute(graph)

    out = tc.to_numpy()                                        # download into a new numpy array
```

### Shape convention (frequent source of bugs)
- `Tensor.ne` is **GGML order** and always the four dims ggml stores, `(ne0, ne1, ne2, ne3)` with unused trailing dims equal to 1 — column-major-ish, the reverse of numpy. `nb` is the matching four byte strides. Only `shape` and `n_dims` follow `ggml_n_dims` (trailing 1-sized dims dropped).
- `new_tensor_Nd` / `reshape_Nd` take dims in **GGML order**, so construct from a numpy array with `*reversed(arr.shape)`.
- To read a result back, `tensor.to_numpy()` allocates an array of `tensor.shape` (the first `n_dims` of `ne`, reversed). Use `tensor.read(out)` with a pre-allocated array to reuse a buffer.
- `tensor.write(x)` accepts an array of `tensor.shape` (1-sized axes are ignored) or a flat one; anything else raises `ValueError`, since it is almost always a numpy-order vs ggml-order mix-up.
- `a.mul_mat(b)` requires `a.ne[0] == b.ne[0]` (shared inner dim) and yields `ne = (a.ne[1], b.ne[1], …)`. For NumPy arrays with matching column counts, `ta.mul_mat(tb)` computes `b @ a.T`. To compute a conventional `left @ right`, store `right.T` as the first GGML operand and `left` as the second.

### Lifecycle rules
- A `Context` must outlive every `Tensor`/`Graph` it produced — `ggml_free` releases all their metadata at once. `Tensor` and `Graph` keep the context alive unless it is explicitly closed, and using one after an explicit close raises `GGMLError` instead of touching freed memory. A `Context` also retains an external `mem_buffer` object for its native lifetime, every other context its ops read tensors from, and the `Buffer`s that `Backend.alloc_ctx_tensors` allocated for it, which in turn retain their `Backend`, so tensor data cannot be garbage-collected out from under a live context.
- Every `Handle` (`Context`, `Backend`, `Buffer`, `GAllocr`, `Scheduler`, `GGUF`) raises `GGMLError` from `.ptr` once closed, so no method can pass NULL into ggml. Always go through `self.ptr` when calling ggml; only lifetime guards read `_ptr` directly.
- Buffers, allocators and schedulers must be freed before their backend. They hold a strong reference to it, and `Backend.close()` closes the ones still open first, so either order works. A `Buffer` nobody references is freed when its context closes.
- `Tensor.write` / `write_raw` / `read` raise `GGMLError` on a tensor with no backend buffer yet; ggml itself would abort the process.
- Op preconditions (`_CHECKS`), arena space for tensors and graphs, and GGUF index/type/name lookups are checked in Python so misuse raises (`ValueError`, `GGMLError`, `IndexError`, `KeyError`) instead of hitting a `GGML_ASSERT` abort. Graph node capacity (`new_graph(size=…)`) is not checked: overflowing it in `build_forward_expand` still aborts.
- For `GGUF`, remember the split ownership above: closing the `GGUF` does **not** close its data `.context`.
- A `Scheduler` must be `reset()` whenever the graph context is: after `Context.reset()` the allocated graph is gone, and the wrapper refuses to compute until the scheduler is reset too.
- A `GAllocr` / `Scheduler` owns the memory of every graph node it allocated. Download results **before** it closes. ggml leaves tensors pointing at freed buffers, so whoever frees a buffer clears the native `buffer` / `data` fields of the tensors it allocated (`buffer.detach`): they become unallocated again, transfers raise `GGMLError`, and ggml would allocate them afresh. This happens when an allocator or scheduler closes, when a larger `reserve()` regrows its buffers (ggml only reallocates when the size grows, which is how the change is detected), and when a `Buffer` closes. A tensor the freer cannot reach, such as a view created in another context after the allocation, is caught by address through `buffer.is_freed` instead, which holds until a new buffer appears at the same address. (In the canonical flow above `tc` is created before `alloc_ctx_tensors`, so it lives in the backend buffer instead and can be read after the allocator closes.)
- `Backend.compute` / `compute_async` raise `GGMLError` for a graph with an unallocated node (never allocated, or its allocator has since allocated another graph or closed); ggml would dereference the NULL data pointer. The check is `Graph._check_allocated`, one pass over the node pointers.
- A `GAllocr` / `Scheduler` holds **one graph at a time**, because every graph is laid out over the same buffers. Right before ggml allocates a *different* graph (another graph, or the same one after nodes were added), the tensors the allocator allocated for the previous graph are detached, whichever context they live in and whether or not the `Graph` wrapper still exists: reading an earlier graph's output then raises `GGMLError` instead of returning the new graph's data, so download results before allocating the next graph. A tensor shared by successive graphs (an input in a long-lived context) is allocated afresh for each and must be uploaded again. The detach has to come first: ggml takes a tensor that still has `data` for one allocated elsewhere and would leave it in memory the new graph reuses or frees. Allocating the unchanged current graph again (`GAllocr.alloc_graph` in a loop, `Scheduler.reset()` then `alloc_graph`) detaches nothing and keeps the data, results stay readable after `Scheduler.reset()` until the next graph is allocated, and tensors in any other buffer (weights or a KV cache from `Backend.alloc_ctx_tensors`, also when written by `cpy` nodes) are never touched. Computing a graph that is no longer the allocated one raises `GGMLError` on both paths: `Backend.compute` finds its nodes unallocated, and `Scheduler` refuses a graph other than the current one.
- A `Tensor` / `Graph` remembers the `_epoch` of its context. `Context.close()` and `Context.reset()` change the epoch, so anything created before raises `GGMLError` when used. Code that wraps a raw tensor pointer must go through `Tensor(ctx, ptr)` on a live context so the epoch is captured.
- All owning wrappers are context managers with idempotent `close()` + `__del__` (from `Handle`). Prefer `with` blocks.

## Adding / changing ops

Every tensor op is generated from a table in `ggbond/ggml/tensor.py` onto both `Context` (`ctx.op(a, …)`) and `Tensor` (`a.op(…)`); none are hand-written. The one exception is an op with no tensor operand (`Context.arange`), which is a plain method on `Context`.

1. Find the `ggml_*` function name in the `ggml-python` bindings (it must already be exposed by ggml-python — this repo cannot add new C bindings).
2. For an op taking one tensor, add `name -> "ggml_funcname"` to `_UNARY_OPS`. For an op taking two tensors, add it to `_BINARY_OPS`. If `ggml_funcname_inplace` exists in the bindings, `name_inplace` is generated automatically with the same parameters and check.
3. For anything with extra arguments, add an entry to `_PARAM_OPS`: `name -> (ggml_funcname, params, doc)`, where each param is `(arg_name, kind)` or `(arg_name, kind, default)` and `kind` is `_TENSOR`, `_TENSOR_OPT` (None becomes NULL), `_INT`, `_FLOAT`, `_BOOL`, `_DTYPE`, or an enum kind (`_POOL_OP`, `_ROPE_TYPE`, `_SORT_ORDER`, `_SCALE_MODE`). Params are listed after ggml's `ctx` and `a`; write docs in terms of ``self`` (the generator rewrites it to ``a`` for the `Context` form). A test checks each entry's arity against the binding.
4. Run `python scripts/gen_stubs.py` to regenerate `ops.pyi`; a test fails while it is out of date.
5. `_make_op` generates the method source for both classes and `exec`s it, so each op gets a real signature (keyword args, defaults, `help()`) with no per-call binding overhead. Only add a hand-written method if a signature genuinely cannot be expressed by the table (nothing currently needs one).
6. ggml checks arguments with `GGML_ASSERT`, which aborts the whole process. If the op has asserts users are likely to hit, add a check to `_CHECKS` that mirrors them and raises `ValueError` (it receives `a` and then the op's arguments positionally). Every generated op also reserves arena space before calling ggml; if the op creates more than one tensor in its context (composites like `conv_2d`), record the count in `_OP_TENSORS`, measured against `Context.used_mem`.
7. Access the underlying ctypes functions via `_ggml` (each module does `import ggml as _ggml`); use the `_ggml` alias rather than a bare `import ggml` so the external package stays visually distinct from the `ggbond.ggml` subpackage.
